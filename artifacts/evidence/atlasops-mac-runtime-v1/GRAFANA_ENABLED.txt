# Grafana: enabled on this Mac's cluster, and what it actually serves
# 2026-10-29T19:16:41Z

## Why it was absent
Not an oversight. infra/local/values/prometheus-local.yaml says:
    # AtlasOps Local Prometheus Stack — low-resource Kind profile
    # Pipeline v1.1 Free-First
    #
    # Preserves: Prometheus, Alertmanager, kube-state-metrics
    # Disables: Grafana (not required for Stage 3/4 gate), admissionWebhooks (avoids webhook patch timeout)
    # Reduces: resource requests for Kind single-node

The canonical infra/values/kube-prometheus-stack.yaml has grafana.enabled: true;
the low-resource Kind profile overrides it to false. The earlier acceptance
report recorded this as BLOCKED, which was the right verdict for the wrong
reason: Grafana was switched off deliberately for a 4-CPU VM, not missing.

## What changed
This VM now has 8 CPU / 12 GiB, so the stack can carry it. Enabled as a
runtime-only helm upgrade with the recorded values plus a Grafana override;
no repository values file was edited.

  chart        : kube-prometheus-stack-88.3.0, app docker.io/grafana/grafana:13.1.3

## Panels that are genuinely empty, and why
node-exporter is not installed in this profile, so every node-level panel
has no source. Confirmed rather than assumed:
    node_cpu_seconds_total             series=0
    node_memory_MemAvailable_bytes     series=0
    node_filesystem_avail_bytes        series=0

So of the 19 provisioned dashboards, the Kubernetes compute/workload and
Alertmanager ones have real data; the Node ones are empty. Reporting both.

## What this is not
No screenshot of the rendered UI was captured: that would mean typing the
generated admin password into a browser, and the panel queries above are
stronger evidence than a picture of them. Grafana is not part of any gate
and nothing here changes a gate status.
